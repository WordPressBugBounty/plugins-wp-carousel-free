# Admin Dashboard — Claude Context

Free's admin dashboard: a trimmed React SPA mounted from two real WP admin submenus (Getting Started, Lite vs Pro) plus a Settings tab reached by a hash link from Getting Started. Registered via `Dashboard::init()`, wired from `bootstrap.php` (same `plugins_loaded` + file-existence-guard shape as `src/Blocks/bootstrap.php`).

**Never grow this beyond what Free ships.** Pro's own dashboard (`../wp-carousel-pro/src/Admin/Dashboard/Dashboard.php`, ~1260 lines) also has Saved Templates/About Us pages, a License tab, and a remote changelog fetch. None of that exists here and none of it should be ported "just in case" — see the root `CLAUDE.md` §2's "never leave complete Pro logic behind a UI check" rule. If Free ever needs one of those, treat it as a new decision, not a resumption of a paused port.

## What exists

- `Dashboard.php` — state reads (`is_module_active()` unchanged since the original shim, plus `is_block_visible()`), `register_menu()`/`reorder_menu()` (native `add_submenu_page()` calls, Figma order: Getting Started → All Carousels → Add New Carousel → Settings → Lite vs Pro → Upgrade to Pro), `enqueue_assets()`, the two AJAX handlers, `render_back_to_settings_link()` (printed on the *Classic* settings page via its `wpcf_options_before` hook), `print_custom_js()` (new, independent of Classic's own Custom CSS output).
- `bootstrap.php` — the only thing `wp-carousel-free.php` requires for this subsystem. It calls `Dashboard::init()` **directly**, not via a hook: it is required from `includes()`, which is itself a `plugins_loaded` callback, and a callback added to the priority currently being iterated is silently never run.
- `img/` — navbar assets exported from Figma (logo, changelog, support, Our Plugins icons).
- `blocks/admin/` (JS) — one SPA, hash-routed, mounted only on the Getting Started page. Nav mirrors the Figma navbar: Dashboard · Blocks · Modules · Saved Templates · Settings · | · Lite vs Pro · About Us · Our Plugins (external) · Get Help. Settings and Lite vs Pro are *also* WP submenu rows that deep-link into their hash.

Only one WP admin page is real (`wpcpf_dashboard`); every other dashboard row is a hash link into it, and `wpcpf_upgrade` redirects out to pricing.

## Which pages are real vs. upsell

`Blocks` and `Modules` are genuinely functional. Block toggles are enforced by `Blocks\BlockVisibility`, in the same three places Pro uses — the editor unregisters the disabled block types client-side from `wpcpBlockLocalize.disabledBlocks` (`blocks/blocks/index.js`), `filter_allowed_block_types` strips them from any *explicit* `allowed_block_types_all` allow-list, and `AbstractBlock::frontend_render_gate()` returns `''` so a disabled block emits no markup and no assets. A disabled block stays **registered** in PHP on purpose: unregistering it would turn every post that already contains one into an unsupported-block error and put that content at risk on the next save. The Lightbox module toggle is the one `is_module_active()` already gates. Lightbox is also the one module with a settings drawer — the gear on its card opens `blocks/admin/modules/`, which reads and writes the same `wpcp_extension_settings` option the block layer already consumes (`AssetManager` localizes it for the editor; `Lightbox_Settings::get_settings()` reads it on the frontend), so a global change lands in both the editor preview and the rendered block with no per-block attribute involved. The drawer reuses the block inspector's own controls, which is why `enqueue_assets()` must load `assets/dashboard/index.css` alongside `style-index.css` and localize `wpcpIconLibraryConfig` for the icon grid. Both pages also list Pro items as inert badged cards — `isPro` rows render no switch and the save handler's slug allow-list rejects them, so a crafted request cannot write them.

**Watermark is the one Pro card whose gear opens a drawer** (decided 2026-08-31, Figma `7492:146024`, which is itself drawn as the locked state). `MODULE_SETTINGS_REGISTRY.watermark` carries `showcase: true` rather than `hasSettings: true`, so `moduleHasDrawerSettings()` — the *Free* drawer predicate — stays false for it, and `ModuleSettingsDrawer` keeps only the header live: the body and footer get `wpcp-module-drawer-showcase` plus `inert`, and the panel is mounted with no props at all, so it never receives a draft or `patchDraft`. `blocks/admin/modules/watermark/WatermarkShowcasePanel.jsx` is a *picture* of Pro's settings — one file, no state, no config or defaults module, no `MediaUpload`, no fetch, and its "Add New Watermark" / "Purge Cache" affordances are `<span>`s, so they are not even focusable. It reuses the real drawer scaffolding (`ModuleDrawerSection`, `ModuleDrawerRow`, `DrawerNumberField`, `DrawerToggleGroupField`, `DrawerToggleSwitch`, `SelectField`) purely for visual fidelity. The green "Upgrade to Pro!" CTA (Figma `7492:192753`) is rendered by the drawer as a **sibling** of the body, not a child — that placement is load-bearing, since a child of the `inert` subtree would not be clickable — and its URL arrives as the `upgradeUrl` prop from the Modules page, which already owns that literal. No PHP changed for any of this, and that absence is the enforcement: `watermark` is in neither `ajax_save_options()`'s `$known` array nor `Module_Settings_Helper::get_registered_modules()`, so `wpcp_extension_settings` has no watermark key to read and nothing posted under one could ever be stored. Do not "finish" this drawer by adding a save path.

The Settings page's `Integrations` tab is functional too. Its six cards toggle `wpcp_integrations_options` — the same option key Pro uses, so the preference survives the upgrade — and `Admin\PageBuilders\Manager` reads it back to decide whether to register each builder's saved-template element. A builder with no stored value is on, matching how the card renders. Every card is switchable whether or not that page builder is installed — detection is Manager's job, so the preference is already stored by the time a builder arrives.

`Saved Templates` is backed by `Saved_Templates.php` — the `sp_wpcp_template` CPT and its shortcode, both named identically to Pro's.

## The one shared option

The Settings tab reads and writes `sp_wpcp_settings` — **Classic's own option**, not a new Free-only one. This is deliberate: `uninstall.php` already reads `wpcf_delete_all_data` from it, and `public/class-wp-carousel-free-public.php` already prints `wpcp_custom_css` from it on the live frontend. Sharing the option means both settings surfaces (the new React tab and the old Classic page) stay one source of truth with zero Classic edits. `scripts/check-block-isolation.js` carries a narrow, commented exception for the literal string `sp_wpcp_settings` for this reason — do not widen it to any other `sp_wpcp_*` symbol.

`wpcp_custom_js` is a new key in that same option with no Classic reader — its only consumer is `Dashboard::print_custom_js()`, which prints it verbatim inside a `<script>` on every frontend page. **Saving it therefore requires `unfiltered_html`, not just `manage_options`** — a multisite site administrator has the latter and not the former precisely so they cannot run script in a Super Admin's session. `ajax_save_options()` skips the key rather than blanking it when the capability is absent, so a value an authorized user saved survives someone else's save, and `enqueue_assets()` localizes `canEditCustomJs` so the field is hidden rather than shown and silently discarded. `wpcp_custom_css` stays at `manage_options` — Classic echoes it into a `<style>`, so it is stripped through `Lightbox_Icon_Helper::sanitize_dynamic_css()` on save instead. That only closes the *dashboard* write path: Classic's own settings page still writes the key, and `public/class-wp-carousel-free-public.php` still `html_entity_decode()`s it before printing, both of which are out of scope while Classic is frozen.

## Diagnostics

Ported from Pro on 2026-09-07 and now a real Free feature, in its own `Diagnostics` class rather than bolted onto `Dashboard`. Opt-in only: nothing is sent until the site owner accepts the admin notice or ticks Share Diagnostic Data on the setup wizard's Finish step. `Diagnostics::set_consent()` is the single write path for both.

**There is no Share Diagnostic Data row on the Settings page** (removed 2026-09-08, product owner's call). The wizard's Finish step is the only dashboard surface, so the wizard — Get Help → Setup Wizard, `#setup-wizard` — is also the only way to *withdraw* consent once granted. `Dashboard::get_options_for_js()` still localizes `diagnosticConsent` and `ajax_save_options()` still accepts it, because the wizard reads and writes it through the same path; do not remove either.

Three divergences from Pro, all forced or deliberate:

- **The notice gate is usage-based, not license-based.** Free has no license, so `maybe_show_notice()` requires at least one published `sp_wp_carousel` or `sp_wpcp_template` — the substitution `easy-accordion-free` already made — in place of Pro's `'valid' === $license_status`. The delay matches Pro at 7 days. Keeping the usage check was reaffirmed on 2026-09-08: dropping it would nag fresh installs that never made a carousel, which is what Pro's license check prevents on its side.
- **Consent lives in standalone options** (`wpcp_allow_diagnostic_data`, `wpcp_ignored_consent_notice`, `wpcp_consent_notice_started`), not inside `sp_wpcp_settings`. Classic's options framework rebuilds that option from its own declared fields on every save (`admin/views/sp-framework/classes/admin-options.class.php:501`), so a foreign key there would be wiped the first time a user saved the Classic settings page.
- **`get_active_plugins()` requires `wp-admin/includes/plugin.php` before calling `get_plugins()`.** Pro and Easy Accordion Free both omit this and call it from a cron callback, where the file is not loaded — a latent fatal. `send()` is also non-blocking, and the block-usage query carries a `LIMIT`; Pro has neither.

`send()` is live as of 2026-09-08, but only from production: it hard-bails on local and private-network hosts with no override hook, so a development install cannot report at all. It also returns on its first statement while `SDR_KEY` is `''`, which is the state to restore if reporting ever has to be switched off.

**The collector route is Free's own, on the production host** (set 2026-09-18, replacing the borrowed Location Weather Pro route): `https://api.shapedplugin.com/wp-json/spda/v1/wp-carousel-free-collect`. `SDR_KEY` is the WP Carousel product-family key, the same value Pro defines as `WPCAROUSEL_SDR_KEY`, so revoking it stops Free and Pro reporting together. `readme.txt`'s Privacy & External Services section discloses this exact URL — WordPress.org requires the disclosure to match, so the two change together.

There is deliberately **no** filter to bypass the host check — adding one puts a "phone home from anywhere" switch in shipped code, so if local testing needs it again, prefer a temporary local edit over a permanent hook.

The cron hook registers before `Diagnostics::init()`'s `is_admin()` guard, because WP-Cron requests are not admin requests. `WPCAROUSELF_URL` and `WPCAROUSELF_VERSION` are the only globals it touches. The API key is a class constant — Free's bootstrap is frozen, so it cannot follow Pro's `define()` — and `send()` returns early while it is empty.

## Setup wizard

Ported from Pro on 2026-09-07, reachable only from **Get Help → Setup Wizard** (`#setup-wizard`). It is a full-page route handled in `Render.js` *before* the hash-to-tab fallback, because it is deliberately absent from `MENU_ITEMS` — without that early return the hash would bounce back to the dashboard. No navbar, no footer; the Toaster is mounted alongside it so step toasts still fire.

**Four steps, not Pro's five.** Welcome → Blocks → Modules → Finish. Pro's License Key step is gone along with its SCSS, since Free has no license; nothing else about the chrome changed.

Both middle steps reuse the dashboard's own components rather than reimplementing them, which is what makes the Pro badges work for free:

- **Blocks** mounts `pages/blocks/template-parts.js`'s `BlockCard`, so a Pro block already arrives with its PRO badge and an inert switch. It lists only the blocks the server sends — `upcomingBlocks` is deliberately *not* rendered here (decided 2026-09-07): the dashboard's Blocks page is where what's coming gets advertised, the wizard is for switching on what ships today.
- **Modules** is the one bespoke card (`wpcpf-sw-module-card`, Figma `4427:191213`): 44px gradient icon, Inter 600 16/20 title, then either a working toggle or — for a Pro module — the shared `.wpcpf-module-pro-badge` pill *in place of* the toggle, so there is no control to click and nothing to post. Pro rows are filtered out of the payload as well, matching the Modules page.
- **Welcome** copy is Figma `4460:180436` verbatim, with one substitution: the description says "WP Carousel", not the design's "WP Carousel Pro". Note the bullets are Pro's feature list and name several things Free does not ship (audio sources, custom players, watermark, password protection, scheduling) — that is the product owner's copy decision, recorded here so nobody "fixes" it back.
- **Finish** closes with the upgrade CTA from Figma `4427:191528` (replaced the earlier Ready Patterns card on 2026-09-07): `#e1f4f6` card, green `#159e2e` button reusing `components/pro/proIcon` and `getPricingUrl()`, and a decorative five-slide stack. The stack keeps the design's fixed slide geometry but is positioned at `left: 42.6%` — the design's 477-of-1121px start expressed proportionally — because the wizard card is narrower than the mock and an absolute `left` puts the artwork on top of the copy. Its three images were downscaled and flattened onto the card colour as JPEG (6.3 MB of Figma PNGs → 120 KB); they are decorative and `aria-hidden`.
- **Finish** writes the diagnostics choice through `saveOptions({ diagnosticConsent })` — the only dashboard consent surface since the Settings row was removed. The checkbox starts **unchecked** unless consent is already stored; Pro pre-checks it, which is not something a WordPress.org plugin should do.

Two traps when porting more of Pro's wizard SCSS. Pro's stylesheet references `var(--wpcp-primary-color)`, which Free does not define — Free's is `--wpcpf-primary-color`, and the silent fallback is a transparent toggle that looks switched off. And `.wpcpf-sw-content-card` is a fixed 515px with `overflow: hidden`: Free's Blocks step has two card sections and the Modules step lists every Pro module, so each *page* scrolls (`max-height: 100%; overflow-y: auto`) instead of each grid carrying Pro's `max-height: 500px`, which stacked past the card and covered the Next button.

## Explicitly not ported from Pro

`pages/license-page/`, Pro's *working* watermark drawer (`WatermarkSettingsPanel`, `WatermarkStyleList`, `WatermarkStyleFields`, `WatermarkImagePicker`, `modules/config/watermark*.js`, the `DrawerAutoNumberField` / `DrawerDualAxisField` / `DrawerPercentField` controls and the `wpcp_clean_wm_cache` AJAX handler — see the showcase note above for what Free has instead), the remote changelog AJAX, and `templates/Sidebar.js` (unused even in Pro's own `Render.js`). If any of these ever becomes a real Free feature, port it deliberately and update this file — do not silently resurrect Pro code because it's convenient to copy.

Pro feature *names* may appear in upsell copy. `scripts/check-block-isolation.js` honours a trailing `isolation-ignore` comment to opt a single line out of the denylist for exactly that — use it per line, never exempt a whole file.
